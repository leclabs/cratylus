The tech lead remembers what is built: its memory holds `realization`, develop's first-parent merge commits, beside the domain model, each the `--no-ff` merge of a feature branch named for its story, its conventional-commit header summarising for an agent reader what it built, its trailer `Story: <name>`, or `Task: <name>` for a task with no story.

The software engineer's task requires `realizedBy`: each merge into develop that realized a concept the task touches, as `{commit, header, realization}`, `realization` being `change` where the concept's meaning holds and `replace` where it changed, the old realization then deleted whole in the same change; it is `[]` where the task touches none. The tech lead's task with no story carries no `realizedBy`. A code review's `verdict` approves only where each concept the change touches has exactly one realization after it.
