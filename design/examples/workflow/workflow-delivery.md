# Examples · workflow delivery

Context: workflow. Concepts: concept journal, reconstitution.

1. (concept journal) **Given** cratylus is installed and a new project has no recorded contexts, **when** its current design, state and context overview are read, **then** the delivered workflow context is available, equal to the release's projected design, under a name qualified by cratylus as its origin and marked delivered and read-only. Reading it does not create a project journal or add any project-owned context.

2. (concept journal) **Given** a project owns a booking context and an unrelated context called workflow, **when** its current contexts and their overviews are read, **then** booking, the project's workflow and the delivered workflow appear as separate contexts. The delivered one is origin-qualified and marked delivered and read-only; neither workflow context replaces, merges with or borrows concepts from the other merely because their plain names match.

3. (concept journal) **Given** cratylus's own project journal holds the very workflow context from which the installed delivered context was projected, and its current wording differs from the installed release, **when** the journal's current design, state and overview are read, **then** only the project's workflow context is shown for that identity, with the project's current wording. The delivered version neither overrides it nor appears as a second copy, even if the delivered release is newer than the branch's own design.

4. (concept journal) **Given** a project can read the delivered workflow context, **when** a writer targets that delivered context to change its description, add or supersede a concept, retire a concept or record a decision, **then** the write is refused because the context is delivered read-only. Neither the delivered design nor the project's journal changes, and the attempted write does not silently create a project-owned substitute.

5. (concept journal) **Given** a project owns an unrelated workflow context beside the delivered one, **when** the architect appends a new version of one of the project's own workflow concepts, **then** the project's journal records that version and its reason, and its own views reflect it. The delivered workflow design and provenance remain unchanged; read-only delivery must not prevent legitimate changes to a distinct project-owned context.

6. (concept journal) **Given** the delivered workflow design contains a live concept whose source has several earlier versions, and the source also has decisions, **when** the reader asks for that delivered concept's history or the delivered context's decisions, **then** no source history or decisions are presented as delivered material. The current delivered meaning remains readable, and its projection is not fabricated into a first historical journal entry or into project-owned decisions.

7. (reconstitution) **Given** a new session starts on a booking project with an open booking decision and a booking cut in flight, **when** it recovers the design before acting, **then** it first reads the booking context overview and the delivered workflow context overview, then the detail needed for the work, from the concept journal and ledger. Its readback to the operator states the current booking design, the delivered workflow practice, the open booking decision and the cut in flight. Tool descriptions or remembered workflow instructions alone do not substitute for reading the delivered practice as a whole.

8. (reconstitution) **Given** a session was compacted after discussing an earlier booking design, and the current branch now records a newer design, a settled decision and a different cut in flight, **when** the session resumes, **then** it recovers the current branch's journal and ledger afresh, reading both the touched project context's overview and the delivered workflow overview before their details. Before acting it reads back the current design and current open decisions and cuts, not the state retained in the conversation or the state of another branch.

9. (concept journal) **Given** one project branch holds the source workflow context by identity while another branch has no record of that identity, **when** each branch's current contexts are read in turn, **then** the first branch shows only its own workflow for that identity and the second shows the delivered workflow. Suppression follows the journal of the branch being read, not an earlier read, another branch or the project's name.

10. (concept journal) **Given** a new project's only available context is the delivered workflow, **when** the architect records the project's first bounded context, booking, **then** the new journal records booking as the project's own context and nothing from the delivered design. Subsequent current views show booking beside the delivered workflow; creating the journal does not make the delivered context disappear or turn it into editable project design.
