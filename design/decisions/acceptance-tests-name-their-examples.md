# Acceptance tests name their examples

An acceptance test is a test, in any language and test framework, whose title is exactly `<context>/<concept>: <example name>`: the context's directory and the concept's file stem under `design/model/`, and the example's `###` heading verbatim, case included, without its ` (judged in review)` marker. One test binds one example, and it lives beside what realizes it.

`cratylus model check` reads source text and runs nothing, so it binds without a test run, a report format or a configured runner, and names each test by `<path>:<line>`. JUnit XML reports were the alternative and lost: they need a prior test run, and frameworks rewrite titles in them (Go's `t.Run` turns spaces into underscores, vitest prefixes `describe` titles). A parser per language (tree-sitter) was the other, and lost to its weight: a grammar per language, and still not every language.

What the check reads as a test:

- A test file is a file outside `node_modules`, `dist` and dot-directories whose name marks it a test by the convention of its language: one of the words of its name, split at `.`, `_`, `-` and at a lower-to-upper case change, is `test`, `tests`, `spec` or `specs` (`basket.test.ts`, `test_basket.py`, `basket_test.go`, `basket_spec.rb`, `BasketTest.java`, `BasketTests.cs`, `BasketSpec.hs`), or a Gherkin feature file, `*.feature`. Prose (`.md`, `.markdown`, `.mdx`, `.txt`, `.rst`, `.adoc`) is never a test file, so a title quoted in a changelog or the docs binds nothing.
- In a feature file, a test is a `Scenario:`, `Scenario Outline:`, `Scenario Template:` or `Example:` line, its title the rest of the line, outside `#` comment lines and doc strings. Gherkin is how a framework whose tests carry no title of their own (a plain pytest function, Rust's `#[test]`, GoogleTest) binds, through Cucumber, Behave, pytest-bdd, SpecFlow, Godog or cucumber-rs.
- In any other test file, a test is a test declaration whose first argument is the title as one whole string literal (`'…'`, `"…"`, or a backtick literal with no `${`), not joined to another by an operator: a call or a command, `name(…`, `name "…"` or `@name(…`, whose name, its last `.` or `::` segment compared case-insensitively and without `_`, is `it`, `test`, `specify`, `example`, `scenario`, `run`, `subtest`, `testing`, `testset`, `testthat`, `testcase`, `testmethod`, `displayname` or `testdox`; or, in C#, F# or Visual Basic, the named argument `DisplayName = "…"` or `TestName = "…"` of a test attribute (`Fact`, `Theory`, `Test`, `TestCase`, `TestMethod`, `DataTestMethod`) in an attribute list, its literal ending the argument (`[Fact(DisplayName = "…")]`). These are the titled declarations of vitest, Jest, Mocha, node:test, Deno, Bun, Go's `t.Run`, Ginkgo, RSpec, minitest, ExUnit, unittest's `subTest`, JUnit 5, Swift Testing, MSTest, xUnit, NUnit, PHPUnit, Pest, Catch2, doctest, hspec, Elm, ScalaTest, Kotest, busted, Dart, clojure.test, Julia, testthat, Zig, Alcotest, Expecto and Test::More. A skipped, focused or table form (`it.skip(`, `it.each(…)(`) is no test.
- A comment is blanked before reading, by the comment syntax of the file's language, known by its extension; a file of an extension the check does not know is read with `//`, `/* */` and `#` comments. A title in a comment binds nothing.

The check matches text, so a title nested in a skipped block or written inside a string is not told from a test that runs; code review judges those. A test that writes fixture test sources composes each test declaration from parts, so the repository's own tests never name an example they do not bind.

The check runs last in `pnpm check`, which fails when it fails. It reads the model's records strictly: a `.md` file anywhere in `design/model/` but `purpose.md`, `<context>/context.md` and `<context>/<concept>.md` is a failure, and an example's body is its Given, When and Then lines in that order, each optionally continued by `And` lines.
