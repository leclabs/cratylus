# Agent Profile Schema (APS)

A generic, declarative specification for defining AI agents independent of any particular framework or runtime. It's expressed as a JSON Schema (Draft 2020-12) so it can validate concrete agent profiles written in JSON or YAML.

## Design principles

- **Declarative, not imperative** — describes *what* the agent is and is allowed to do, not the control-flow code that runs it.
- **Portable** — no vendor-specific fields at the top level; provider/runtime specifics live in clearly namespaced `x-*` extension blocks.
- **Composable** — agents can reference sub-agents and shared tool/policy libraries by id.
- **Separable concerns** — identity, cognition (model+instructions), capability (tools), memory, guardrails, orchestration, and ops are distinct top-level blocks so each can be validated, versioned, and reused independently.

## 2. Example instance

```yaml
apiVersion: agent-profile/v1
kind: Agent
metadata:
  id: support-triage-agent
  name: Support Triage Agent
  version: 1.2.0
  description: Classifies and routes inbound support tickets.
  owner: support-eng@example.org
  tags: [support, triage]

spec:
  persona:
    role: Customer support triage agent
    instructions: |
      Classify each incoming ticket by urgency and category, then either
      answer directly from the knowledge base or escalate to a human.
    goals:
      - Resolve common questions without human involvement
      - Never leave a ticket unclassified
    nonGoals:
      - Do not issue refunds or account changes directly

  model:
    provider: anthropic
    name: claude-sonnet-5
    parameters:
      temperature: 0.2
      maxOutputTokens: 1024
    fallback:
      - provider: anthropic
        name: claude-haiku-4-5-20251001

  capabilities:
    tools:
      - id: search-kb
        description: Search the support knowledge base
        inputSchema: { type: object, properties: { query: { type: string } }, required: [query] }
        permission: auto
        sideEffects: none
      - id: create-ticket-escalation
        description: Escalate a ticket to a human agent
        inputSchema: { type: object, properties: { ticketId: { type: string } }, required: [ticketId] }
        permission: confirm
        sideEffects: reversible
    modalities:
      input: [text]
      output: [text, structured]

  memory:
    shortTerm:
      strategy: sliding-window
      windowSize: 20
    longTerm:
      enabled: false
    knowledgeSources:
      - id: kb-main
        type: document-store
        refreshPolicy: scheduled

  io:
    inputSchema: { type: object, properties: { ticketText: { type: string } }, required: [ticketText] }
    outputSchema:
      type: object
      properties:
        category: { type: string }
        urgency: { type: string, enum: [low, medium, high] }
        response: { type: string }
    responseFormat: json

  guardrails:
    deniedActions: [issue-refund, delete-account]
    humanApproval:
      required: true
      triggers: [urgency=high, category=billing]
    escalation:
      onFailure: human-handoff
      maxRetries: 2

  orchestration:
    mode: single-agent

  observability:
    logging: verbose
    tracing: true
    metrics: [tool_call_count, escalation_rate]
```

---

### Notes on extending this

- **Templates**: an `AgentTemplate` (via `kind`) can hold shared `guardrails`/`observability` blocks; concrete agents pull them in via `metadata.inherits`.
- **Multi-agent systems**: use `spec.orchestration.subAgents[].ref` pointing at other profile `id`s — the schema stays flat and file-based, so a fleet of agents is just a directory of profiles plus one supervisor profile.
- **Runtime binding**: `capabilities.tools[].id` and `lifecycle.*` intentionally hold references (strings), not code — the executing runtime resolves them, keeping the profile portable across engines (LangGraph, a custom orchestrator, Claude Agent SDK, etc.).

Want this narrowed to a specific runtime (e.g. mapped onto the Claude Agent SDK's actual config surface), or saved to a file in a project?
